# H200 and B200 sessions: the H100 plan, plus speculative decoding

**Status: proposed; nothing has been measured.** The user asked for this guide on 2026-10-10. It is written for an agent who will run a measurement session on one of two servers.

| Server | GPUs | Proposed study identity |
| --- | --- | --- |
| H200 | 4 × H200 | `five-model-rerun-h200-v1` |
| B200 | 4 × B200 | `five-model-rerun-b200-v1` |

Each server gets its own session, its own study identity and its own controls. Run a session only on a server the user has handed over, and only for the hours the user states. This guide does not authorize renting anything.

The work is [the 15-hour session](../target.md#the-15-hour-session) defined for 8×H100, with two differences:

1. **Speculative decoding is added.** On H100 it is deferred. Here each supported method runs against a fresh autoregressive (AR) baseline of the same model.
2. **Checkpoints are handled one at a time**, because both servers have little free storage. [Checkpoint storage](#checkpoint-storage-one-model-at-a-time) gives the procedure.

## What a session delivers

For each server, on all five models:

- **Kan's questions first.** The architecture as this server executes it; attention-path time in prefill and decode at 1K/16K/64K/128K; stored state bytes; expert time. Expert-routing statistics and HBM counters if their gates pass.
- **AR serving.** 2,048-token outputs at 1 and 16 clients, with 1K/16K/64K inputs, in three blocks.
- **Speculative decoding.** Each supported method against the same model's AR runs, at 1 and 16 clients, with 1K/16K inputs, in three blocks.
- **A ledger** that marks every planned cell as valid, failed, unsupported or pending.

## What changes from the H100 plan

| Item | 8×H100 session | H200 or B200 session |
| --- | --- | --- |
| GPUs | 8, tensor parallel 8 plus expert parallel | 4, tensor parallel 4 plus expert parallel: `CUDA_VISIBLE_DEVICES=0,1,2,3`, `--tensor-parallel-size 4 --enable-expert-parallel` |
| Node totals | Per-rank value × 8 | Per-rank value × 4 |
| Speculative decoding | Deferred | Runs |
| Checkpoints | All five on disk | One at a time, the shared pool first |
| Model order | Rotates inside each block | Fixed: one model finishes before the next starts |
| Runtime | Latest vLLM build, frozen at preparation | The same frozen commit if it supports the GPU; otherwise a separately recorded runtime block |

**Runtime on the 4×H200 node (2026-10-10).** The node's driver is 570.211.01, which supports CUDA 12.8 at most. The rerun build `c41b2639e` (vLLM `0.31.1rc1.dev261`) links CUDA 13 and fails to import here (`libcudart.so.13`). vLLM `0.20.0` and later also link CUDA 13, so the newest build that runs on this driver is the **0.19.1** release, with `torch==2.10.0+cu129`, in `~/vllm-h200-cu12` ([install.sh](../install.sh)). That is a separately recorded runtime block with fresh controls, not the rerun build. Pending before any measurement: a smoke test inside an allocation that loads one model and answers one request, and the wheel hashes.

Everything else is the same as on H100: memory utilization 0.90, context limit 262144, at most 64 sequences, an 8,192-token prefill chunk, text only, native precision (Qwen original BF16, GLM native FP8), temperature 0, thinking off where supported and `reasoning_effort=low` for GLM, the same frozen prompts and request lists, and three blocks behind every published number. Prefix caching is off in every launch. Only 2,048-token outputs are measured: no 256-token and no 8,192-token runs.

Verify these on the server; do not assume them:

- **Memory.** An H200 is specified at 141 GB. Read the B200's memory from `nvidia-smi`; this guide assumes no value. October's weights over eight GPUs, divided by four, give about 40, 73, 40, 63 and 78 GiB per GPU for 0731, V4.1, MiMo, Qwen and GLM. That is an estimate. Record each model's `Model loading took` and `Available KV cache memory` lines.
- **Kernels.** Another GPU generation can select other attention, dense and expert kernels and another KV format. Read each model's class, precision and backends from this server's log and traces. The H100 notes in [models.md](models.md) are a checklist, not evidence for this server.
- **Host RAM.** V4.1 keeps its Engram tables in pinned host memory (about 190 GB over eight ranks in October), and Qwen keeps an embedding there. Check `free -h` before launching them.
- **Capacity.** If 128K at actual B=8, or 16 clients at 64K, does not fit, record a capacity limit. Do not retry with a smaller batch and report it as the same point.

**Comparison limits.** 8×H100, 4×H200 and 4×B200 differ in GPU count, parallel width, memory, GPU generation, CPU and driver. A number from one is never a control for another. Within one server the five models share the hardware, but they are measured one after another, so their comparison carries a time-order caveat.

## Checkpoint storage: one model at a time

Measure the models in this order on both servers. The first three have candidate speculative methods.

| Order | Key | Download size | Speculative arms |
| ---: | --- | ---: | --- |
| 1 | `v4-0731` | 156 GB | DSpark |
| 2 | `mimo-v26` | 166 GB | MTP, DFlash |
| 3 | `v41` | 476 GB | DSpark |
| 4 | `glm-53` | 306 GB | None yet |
| 5 | `qwen-38-bf16` | 360 GB | None yet |

Sizes are October's; the checkpoint and revision of each key are in `bench/serve.sh` and on its [reproduce page](../reproduce/README.md#the-five-models). Two locations matter:

- `HF_POOL`: the server's shared Hugging Face pool, the directory that contains `hub/`. The user gives its path. It is read-only for this work: never download into it, change it or delete from it.
- `HF_HOME`: this session's own cache. Downloads go here, and only here may a checkpoint be deleted.

For each model, in order:

1. **Check the pool.** Run the check below against `$HF_POOL/hub`. If it prints `COMPLETE`, use the pool copy: launch with `HF_HUB_CACHE=$HF_POOL/hub HF_HUB_OFFLINE=1`, and skip steps 2, 3 and 6.
2. **Check free space.** `df -h "$HF_HOME"` must show at least the download size plus 50 GB for traces, results and caches. If the checkpoint does not fit, mark the model pending with the reason and go to the next one. Do not start a partial download.
3. **Download this one model** into `$HF_HOME` with the `hf download … --revision …` command on its reproduce page. Run the check again against `$HF_HOME/hub`; continue only on `COMPLETE`. No other download runs while a model is being measured.
4. **Measure** the whole [per-model procedure](#per-model-procedure). The speculative drafts ship inside the same checkpoint, so every launch of the model, AR and speculative, happens before step 6.
5. **Close the model.** Stop the server and confirm 0 MiB on all four GPUs. Check that every planned cell is accounted for and that the raw results are valid and stored where the user asked. Build the component table from the profiler traces, then move the traces off the node or delete them: they are large and count against the free space.
6. **Remove the checkpoint**, only if this session downloaded it, with the guarded command below. Confirm the space came back with `df -h`.
7. **Log it.** Append one line per model to `results/<study>/_logs/checkpoints.jsonl`: key, revision, `pool` or `downloaded`, path, bytes, and the deletion time or `kept (pool)`.

If the pool path is unknown, or its layout is not `hub/models--<org>--<name>/snapshots/<revision>/`, ask the user. Do not search the filesystem for checkpoints.

The check compares every file in the cached snapshot with the size the Hub reports for the pinned revision:

```python
"""Usage: python pool_check.py <repo> <revision> <hub-cache-dir>. Exit 0 only if the snapshot is complete."""
import sys
from pathlib import Path
from huggingface_hub import HfApi

repo, rev, cache = sys.argv[1], sys.argv[2], Path(sys.argv[3])
snap = cache / f"models--{repo.replace('/', '--')}" / "snapshots" / rev
files = HfApi().model_info(repo, revision=rev, files_metadata=True).siblings
bad = [f.rfilename for f in files if not (snap / f.rfilename).is_file() or (snap / f.rfilename).stat().st_size != f.size]
print(f"{repo}@{rev[:8]}: " + ("COMPLETE" if not bad else f"INCOMPLETE, {len(bad)} of {len(files)} files missing or wrong size"))
sys.exit(1 if bad else 0)
```

It needs network access to the Hub and was tested on a small public repository on 2026-10-10, not on these checkpoints.

Removal, for a checkpoint this session downloaded:

```bash
: "${HF_HOME:?}" "${HF_POOL:?}" "${MODEL:?}"            # MODEL is the repository name, for example org/name
REPO_DIR="$HF_HOME/hub/models--${MODEL//\//--}"
case "$REPO_DIR/" in "$HF_POOL"/*) echo "refusing: inside the shared pool" >&2; exit 1 ;; esac
du -sh "$REPO_DIR" && rm -rf -- "$REPO_DIR" && df -h "$HF_HOME"
```

Delete one named directory at a time. Never use a wildcard, and never delete a directory the checkpoint log does not list as `downloaded`.

## Per-model procedure

Every launch owns its server, waits for readiness, and stops the server on success, error or timeout. Config names are those of `bench/serve.sh`.

| Step | Launch | Config | What it runs |
| ---: | --- | --- | --- |
| 1 | Diagnostics, once | `off-profidle` | First load. Class, precision, backends and KV format from the log. Functional check with 12 natural-ending prompts. Pilot of the serving points. 12 traces: prefill at 1K/16K/64K/128K, and decode at actual B=1 and B=8 on the same four contexts. State snapshots at the eight decode conditions |
| 2 | Expert-routing statistics, once | Instrumented | As defined in [Experiments for the blog](../target.md#experiments-for-the-blog). Limit: 15 minutes |
| 3 | HBM counters, once | Under the counter tool | As defined in [Experiments for the blog](../target.md#experiments-for-the-blog). Limit: 15 minutes |
| 4 | AR timing, three blocks | `off` | The six serving points below, plus unprofiled decode intervals of 512 tokens per request at actual B=8 on 1K/16K/64K/128K and at B=1 on 128K |
| 5 | Speculative timing, three blocks per supported arm | `dspark-fixed-k5`, `mtp-k3` or `dflash-k7` | The four paired points below |

| Serving points | Output tokens | Clients | Requests per run | AR | Speculative |
| --- | ---: | ---: | ---: | --- | --- |
| 1K, 16K | 2,048 | 1 | 12 | Yes | Yes |
| 1K, 16K | 2,048 | 16 | 48 | Yes | Yes |
| 64K | 2,048 | 1 | 12 | Yes | No |
| 64K | 2,048 | 16 | 48 | Yes | No |

Per server that is 90 AR runs, and 12 runs for each speculative arm: 48 if all four candidate arms work.

- **Blocks.** A block is one AR launch followed by one launch for each supported arm. Reverse that order in block 2. The AR run of a block is the baseline for the speculative runs of the same block.
- **Validity.** A run is valid when every request completes with exactly 2,048 output tokens and none fails. Keep failed attempts and slow blocks in the evidence.
- **Short runs.** If the pilot shows a point lasting under 60 seconds on the fastest model, double that point's requests (24 or 96) for every model on that server, and record the change.
- **Gates.** Steps 2 and 3 need instrumentation that did not exist in October. Decide each on the first model of the server: with no valid result within 20 minutes, skip that step for every model on the server and report the fallback from the [answer map](../target.md#answer-map-for-the-brief).
- **Drift.** The three blocks of a model are consecutive launches, so they show launch-to-launch variation, not drift across the session. If one model's checkpoint is in the pool, rerun its 16K one-client AR point at the end of the session and report both values. If none is in the pool, there is no drift control; say so in the report.

## Speculative comparison

Follow the [speculative design](../target.md#speculative-comparison) in target.md, at this session's two loads.

| Model | Arm and config | Check before timing |
| --- | --- | --- |
| `v4-0731` | DSpark, fixed, width 5: `dspark-fixed-k5` | The loaded method and width in the log; the draft pinned to the same revision. No classic MTP is assumed |
| `v41` | DSpark, fixed, width 5: `dspark-fixed-k5` | The method that actually loaded. Do not infer it from `mtp.*` weight names |
| `mimo-v26` | MTP, width 3: `mtp-k3`. DFlash, width 7: `dflash-k7`, with the drafter in the `dflash/` folder of the same snapshot | The loaded MTP depth and the DFlash drafter path |
| `glm-53`, `qwen-38-bf16` | None yet: their support audit is pending | Decide before the session from source and checkpoint. Otherwise run AR only and report "speculation: not audited" |

- **Pairs.** Output length, prompts, request lists, build, precision, sampling, cache policy and hardware are identical inside a pair. Report the speculative-to-AR ratio for each block, for throughput, TPOT and TTFT. A ratio below 1 is a result and is reported.
- **Answers before speed.** Before the timed runs, run the 60-task natural-ending set (20 per domain, as target.md requires) twice with AR at the same seed and once with each arm, at 1 and at 16 clients. Record token agreement where the method promises it, task results, truncation and natural lengths. Forced 2,048-token runs measure speed only; they do not show that an answer is still correct.
- **Counters.** Collect proposed, verified, accepted and committed tokens and verification rounds, with their denominators. A missing counter stays empty; do not derive it from streamed text chunks.
- **Status, not fallback.** A method that this build does not support on this GPU is reported as unsupported. Do not switch to an older runtime, another width or another method on the node.
- **No winner selection.** Each arm keeps its own result. A difference inside the 5% threshold or the spread between blocks is unresolved.

## Order, budget and stopping

No timing exists for these servers, so the hours below are a guess to be replaced. The H100 session is 15 hours; the speculative arms would add about 4 hours there, and one-at-a-time downloads up to 2 more.

- **Project after the first model.** Take the time the first model used without its download, scale it by each remaining model's run count, add the downloads, and compare the total with the hours the user gave.
- **If it does not fit,** drop the 16-client runs at 16K, AR and speculative. If that is not enough, drop all 16-client runs. Use the same matrix for every remaining model. Keep the diagnostics and the one-client AR and speculative runs.
- **Never fewer than three blocks** behind a published number. Drop points, not blocks.
- **Before each model,** the time left must cover its download and its whole procedure. Otherwise stop and leave it pending; a model that cannot finish is not started.
- **Unused time is returned.** It is not filled with a measurement this guide does not list.
- **On every exit,** stop the server and confirm 0 MiB on all four GPUs.

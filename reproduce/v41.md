## 1. Download

476 GB took about 4 minutes on the first node.

```bash
export HF_HOME=/workspace/hf HF_XET_HIGH_PERFORMANCE=1
hf download deepseek-ai/DeepSeek-V4.1-Flash --revision dba1be0a40aa45a94ad051997016db3960a90277 --max-workers 32
```

Check host memory before launching: `free -g`. This model keeps about 190 GB pinned in host RAM (see the notes).

## 2. Launch

```bash
export VLLM_VENV=/root/vllm-latest HF_HOME=/workspace/hf
bash bench/serve.sh v41 off /tmp/serve-v41.log --max-num-batched-tokens 8192
```

For this model `bench/serve.sh` adds `--tokenizer-mode deepseek_v41 --reasoning-parser deepseek_v41 --tool-call-parser deepseek_v41`. The full command it runs, after setting the [common environment](README.md#common-setup):

```bash
vllm serve deepseek-ai/DeepSeek-V4.1-Flash \
  --revision dba1be0a40aa45a94ad051997016db3960a90277 \
  --host 0.0.0.0 --port 8000 \
  --tensor-parallel-size 8 --enable-expert-parallel \
  --language-model-only \
  --tokenizer-mode deepseek_v41 --reasoning-parser deepseek_v41 \
  --enable-auto-tool-choice --tool-call-parser deepseek_v41 \
  --gpu-memory-utilization 0.90 \
  --max-model-len 262144 \
  --max-num-seqs 64 \
  --no-enable-prefix-caching \
  --max-num-batched-tokens 8192
```

## 3. Check the log

| Line | Meaning |
| --- | --- |
| `Resolved architecture: DeepseekV41ForCausalLM` | Right model class |
| `Decoder SWA bounded replay: in eager prefill steps, layers 21-39 run on each request's last 128 tokens only.` | **The prefill skip is on.** If this line is missing, prefill runs all 40 layers on every token and will be much slower |
| `Resolved Engram configuration: EngramConfig(cpu_offload=True, …)` and `Engram table offloaded to pinned host memory: … 11.80 GiB per rank` (twice) | Engram tables live in host RAM: about 190 GB of pinned memory for 8 ranks |
| `Using 'HUMMING' Mxfp4 MoE backend`, `DeepSeek V4 expert_dtype resolved to 'fp4'` | 4-bit experts |
| `Using DeepSeek's fp8_ds_mla KV cache format` | FP8 KV (the model card's smallest KV figure assumes FP4) |
| `Setting kv cache block size to 64` | 64-token KV blocks |
| `Model loading took 36.32 GiB`, `Available KV cache memory: 29.14 GiB`, `GPU KV cache size: 9,092,347 tokens` | Largest weights, smallest pool of the three DeepSeek and MiMo deployments |

Then run the [health check](README.md#health-check-after-any-launch).

## 4. Send a request

```bash
curl -s localhost:8000/v1/chat/completions -H 'Content-Type: application/json' -d '{
  "model": "deepseek-ai/DeepSeek-V4.1-Flash",
  "messages": [{"role": "user", "content": "What is 17 * 23?"}],
  "max_tokens": 64, "temperature": 0, "chat_template_kwargs": {"thinking": false}}'
```

The answer should contain no reasoning text and end with `finish_reason` `stop`.

## 5. Measure

Stop the hand-launched server first. The chain starts its own. It needs the rebuilt inputs and a frozen plan from the [procedure](README.md#3-rebuild-public-inputs).

```bash
export BLOG_STUDY=blog-architecture-h100-v1
bash bench/blog_launch.sh diag-v41 diag:v41          # functional check, pilot, live KV, traces
# wait for the chain to exit, then:
bash bench/blog_launch.sh timing-v41 timing:v41:1    # six unprofiled points of block 1
tail -f results/$BLOG_STUDY/_logs/chain.log
```

## Known problems and notes

- **Needs the most host RAM** (weights in the page cache plus Engram tables). The node had 1.7 TB; check `free -g` on a smaller one.
- **The prefill skip is build-dependent.** The older pinned build (`44af287e…`) ran all 40 layers on every prompt token, which is why the September V4.1 prefill numbers were slow. Confirm the `bounded replay` log line on any new build before comparing prefill.
- **The prefill skip does not apply** to steps under 768 tokens or to requests asking for prompt logprobs. See the [prefill check](../reports/blog-architecture-h100-v1/v41_prefill_check.md).
- **Its decode step is split over several GPU streams.** When reading traces, cut steps at the CPU-side annotation ([lesson 3](../teach_me/03_traces_and_components.md)). Summing only the main-stream span saw 7–57% of the step.
- The harmless warnings `Attempted to load weight image_newline …` come from the unused vision part.

01

What are we comparing?

Qwen has the highest throughput in five of six tests. MiMo leads on short prompts with one client. V4.1 uses the least memory for a live conversation.

These models reduce computation in different ways. Some attend to fewer earlier tokens; others run only a few of their available neural networks, called experts. The question is whether those savings translate into faster answers and lower memory use.

First, read the prompt

A token is a small piece of text, such as a word or part of a word. During prefill, the model processes the prompt. Long prompts are split into chunks.

Then, generate the answer

During decode, the model generates one token per active request per step. A response therefore includes both prompt processing and repeated generation steps.

A shared setup. All five use the same vLLM build, eight H100 GPUs, serving limits, public code/math/chat requests and 256-token answer length. We test approximately 1K, 16K and 64K input tokens with one or eight active clients. 1K means roughly 1,000 tokens; c8 means eight active clients. Model-specific precision and the recorded machine differences are covered in the measurement notes.

These results compare deployed models, including their software and precision settings. They do not measure answer quality or rank architecture alone.

02

Which model serves faster?

Throughput is the total number of output tokens produced per second across all clients. Latency is how long an individual client waits. Serving more requests at once can raise throughput without making each answer arrive sooner.

Reading the controls: time to first token (TTFT) measures the initial wait; time per output token (TPOT) measures the average wait per later token; end-to-end latency measures the whole response. “p50” means the median request in a run.

03

Two kinds of work inside a layer.

A model has many layers. In each layer, attention retrieves information from earlier tokens, and a feed-forward network (FFN) transforms the token’s representation. In a mixture-of-experts model (MoE), a router chooses which expert FFNs to run. A shared expert runs for every token.

The cards show the main differences. Recurrent state is updated in place instead of retaining a separate record for every past token. Sparse attention selects some past positions to read. The two mechanisms can coexist in one model.

05

Fast lookup does not mean small memory.

To avoid recomputing the past, attention keeps keys and values (KV): vectors derived from earlier tokens. Hybrid models also keep recurrent state. We call the memory occupied by active requests live state.

For one live request in the 64K bucket, V4.1 uses about 0.93 GiB across eight GPUs, versus 6.97 GiB for Qwen. The charts use vLLM 554340f3; Qwen was measured on the second node. A GiB is about 1.07 billion bytes.

Three different quantities: weights are the learned model parameters; the reserved KV pool is memory set aside for requests; live state is the occupied part of that pool. A smaller live-state footprint does not by itself establish maximum concurrent requests.

What remains unknown

Storage is not memory traffic.

HBM is the GPU’s high-bandwidth memory. State size tells us how many bytes are held there; traffic counts how many bytes are read and written while computing. Hardware traffic counters were not collected, so these results cannot identify which model moves the fewest bytes.

Live bytes are estimated from cache occupancy and the reserved pool. Block rounding and different actual token counts affect the values. Prefix caching—reusing saved prompt computation across requests—was off, so reusable-prefix capacity was not tested.

06

Expert count alone does not predict speed.

Choosing fewer experts saves work, but experts differ in size. Their computation also depends on numerical precision and the GPU implementation. An expert kernel is the software that performs its matrix multiplications.

Qwen selects more experts per token than MiMo, but each is much smaller: width 640 rather than 2,048. Width is the size of an expert’s intermediate vector. Its expert computation therefore need not be more expensive just because it selects more experts.

GLM illustrates the role of implementation. In the late 64K prefill chunk, its expert kernels take 25.1 ms, versus 244.0 ms for MiMo on the same node and vLLM 554340f3. Their experts have the same hidden and intermediate dimensions, but the deployments use different precision and kernels. This observation motivates a controlled backend test; it does not prove that changing MiMo’s precision would reproduce GLM’s result.

BF16 stores 16-bit floating-point weights; FP8 uses 8-bit formats, and FP4/MXFP4 use 4-bit formats. Fewer bits can reduce storage, but do not guarantee a faster kernel. The runtime chose unquantized Triton experts for Qwen, FP8 FlashInfer CUTLASS for GLM and 4-bit HUMMING for the DeepSeek and MiMo deployments.

Keep the three ideas separate. Attention sparsity selects past positions. MoE sparsity selects expert networks. Quantization reduces numerical precision. Each changes a different part of the cost.

Tokens per expert, routing imbalance and padding were not measured. We therefore cannot claim that uneven expert use caused a bottleneck.

07

Measurement notes and evidence.

All five models use the same core serving setup: vLLM 554340f3d3259e321be4c07282be7a02a5aeef83, eight H100 80GB GPUs, the same serving limits and public request lists, and 256 forced output tokens. Each of the six workloads was repeated three times, for 90 main timing runs. GPU profiling and live-state snapshots were collected separately.

Qwen3.8-Flash-Next means the original BF16 checkpoint throughout this article. It ran on a second machine with the same GPU model and count, but a different CPU and driver. MiMo was repeated there as a control: its throughput was 0.983–0.995× the first machine’s result. We compare throughput across machines and keep Qwen’s latency separate, because the control’s first-token wait and time per token with eight clients changed.

Other limits: GLM used its lowest reasoning effort because it has no thinking-off switch; the other models disabled thinking. Model order was not rotated across all five. Some timing windows were under 60 seconds, and slow first runs remain included. Three repeats and forced-length answers do not establish answer quality, production tail latency or maximum serving capacity.

Shared serving configuration

TP8 splits tensor computation across eight GPUs; expert parallelism distributes experts across them. Memory utilization is 0.90, maximum context is 262,144 tokens, maximum sequences is 64, and the prefill chunk budget is 8,192 tokens. The tested client loads are one and eight, not 64. Temperature is zero; speculation and prefix caching are off. Each model uses its released precision, with no additional quantization.

The version is 0.31.1rc1.dev50+g554340f3d. Exact checkpoint revisions, requests, counts and collection rules are in the source-selection record and linked study plans.
